Java4Shell — how it really works

CVE-2026-114938 · OpenJDK Base64 decoder

A memory bug that lives inside the JVM, not in your app code.

Status (per Hadrian, Nov 17 2026): CVE reserved, no public description,
no confirmed vendor advisory, no exploitation reported. Treat as unverified.

1 · Why Java is usually safe

Every array access is bounds-checked

byte[] out = new byte[1]; out[3] = 0x41; // ← Java throws ArrayIndexOutOfBoundsException // memory is protected. no corruption.
So application code cannot normally overflow memory. That's why this class of bug is rare in Java.

2 · The JVM swaps in hand-written assembly

On AVX-512 CPUs, Base64 decode becomes a native "intrinsic"

your code
Base64.decode()
→
HotSpot JIT picks
which implementation?

Pure Java decoder

Bounds-checked. Safe. Used on ARM / older CPUs.

AVX-512 intrinsic (JDK-8268276)

Raw pointers, no bounds checks. On by default. The bug lives here.

3 · A length miscount writes past the buffer

Proven safely with a tiny native model + AddressSanitizer

// "Mw==" should decode to 1 byte. Buggy loop writes 3. ==ERROR: AddressSanitizer: heap-buffer-overflow WRITE of size 1 ... 0 bytes after a 1-byte region in decode_buggy minibase64.c:49 // WITHOUT sanitizer (a normal JVM): exit=0, no error → the extra bytes silently corrupt adjacent heap memory
Caught in the lab ·vs· silent in production — that contrast is the vulnerability.

5 · Detect & mitigate

Verifiable, safe, today

🔎 Find exposure: Java 17.0.6+/21/25 on x86 with grep avx512_vbmi /proc/cpuinfo
🧪 Hunt the bug: differential fuzz the two decoders + run the JVM under AddressSanitizer
🛡️ Interim mitigation: -XX:-UseBASE64Intrinsics → intrinsic drops out, app still works
✅ Real fix: patched JVM per your vendor's advisory (confirm it names this CVE)
Your app code can be clean and still exposed — the defect is below it, in the JVM.
